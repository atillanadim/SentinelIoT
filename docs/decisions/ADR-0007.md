# ADR-0007 — Mecanismo de helper privilegiado

**Data:** 2026-11-08
**Status:** aceito, implementação na Fase 5

## Contexto

O agente deve rodar sem root. nftables exige privilégios. Executar o agente como
root aumenta o impacto de uma falha.

## Alternativas

1. Helper separado via Unix domain socket, com operações permitidas.
2. Agente root.
3. Regras de sudoers para comandos nft.
4. Binário setuid.
5. Container privilegiado.

## Decisão

- Helper mínimo, executado como root.
- Comunicação por Unix domain socket local, com permissões restritas.
- Protocolo JSON com operações predefinidas: bloquear, desbloquear, listar.
- Validação de IP, TTL, rule_id e motivo.
- Nenhum comando shell arbitrário.
- Nenhum nome de tabela/cadeia fornecido pelo cliente.
- Operação somente na tabela/cadeia própria do SentinelIoT.
- Auditoria de cada operação.
- Socket não exposto à rede.

## Justificativa

Isola o privilégio em um componente pequeno, testável e com interface fechada.
Evita sudoers amplo e setuid.

## Consequências

- Instalação e serviço adicionais na VM.
- Necessidade de permissões de grupo para o socket.
- Testes específicos de rejeição de parâmetros inválidos.
- O helper precisa de atualização coordenada com o agente.

## Riscos

- Um bug no helper pode afetar o firewall.
- Permissões frouxas no socket permitem abuso local.
- O helper precisa validar tudo, mesmo que o agente já valide.

## Evidência de validação

Pendente: testes de helper na Fase 5, em VM com snapshot.
