# ADR-0014 – Runtime local de honeypots em Python no MVP

**Data:** 2026-11-12
**Status:** aceito; substituível pelo runtime em container na Fase 1

## Contexto

A Fase 0 entregou a estrutura do projeto, a configuração e o laboratório Linux,
mas ainda não havia honeypot, agente, banco ou CLI funcionais. O objetivo desta
etapa é ter um ciclo completo de demonstração e operação assistida no host de
desenvolvimento, sem alterar firewall e sem depender de Docker.

O caminho oficial do produto continua sendo o runtime isolado em container na VM
Linux. Porém, o ciclo de feedback no Windows era longo: cada ajuste de isca,
coleta ou decisão exigia provisionar o container antes de validar a lógica.

## Alternativas

1. Implementar primeiro o honeypot em container e só depois a CLI.
2. Criar apenas simulações da CLI, sem servidores de rede reais.
3. Implementar servidores-isca locais em Python, com a mesma interface de
   eventos e estado que o runtime em container usará depois.
4. Usar uma ferramenta externa de honeypot e adaptar a CLI a ela.

## Decisão

- O MVP executa servidores-isca locais em Python para HTTP, SSH e Telnet.
- As interações são gravadas em um spool JSONL append-only e consumidas por um
  coletor incremental para SQLite.
- O agente roda como daemon local, reconcilia o estado persistido das iscas e
  coleta eventos periodicamente.
- A CLI e o shell interativo usam os mesmos comandos, e a lista de ban registra
  decisões do administrador (`pending`, `blocked`, `allowed`, `ignored`,
  `allowlisted`).
- Nenhuma regra de firewall é aplicada. `blocked` é apenas uma decisão
  registrada e auditável.
- O caminho `Docker` continua planejado para a Fase 1, reutilizando o mesmo
  contrato de spool, eventos, banco e CLI.

## Justificativa

Permite validar o fluxo de ponta a ponta (isca -> evento -> banco -> decisão)
sem elevar privilégios, sem tocar no firewall e sem depender de uma VM ligada.
Os servidores falsos não armazenam corpos, senhas ou payloads e escutam apenas
em loopback por padrão.

## Consequências

- O runtime local não substitui o isolamento do container nem a homologação na
  VM Linux.
- O contrato do spool JSONL e do banco precisa permanecer compatível com o
  runtime em container.
- O modo `observe` continua sendo o padrão; `enforce` permanece bloqueado por
  validação de configuração.
- A decisão `blocked` não produz efeito de rede nesta fase.

## Riscos

- Confundir a demonstração local com um honeypot exposto em produção.
- Portas locais publicadas em `0.0.0.0` por configuração incorreta.
- Divergência entre o comportamento dos servidores Python e a imagem oficial.
- Acúmulo de eventos de teste no banco de desenvolvimento.
