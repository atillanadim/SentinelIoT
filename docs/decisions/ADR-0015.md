# ADR-0015 – Runtime de honeypots em container na Fase 1

**Data:** 2026-11-12
**Status:** aceito; substitui o runtime local como caminho oficial, sem removê-lo

## Contexto

A Fase 0 entregou o laboratório Linux isolado e validou o Docker static na VM
`sentinel-lab`. O MVP local (ADR-0014) provou o fluxo completo (isca -> spool
JSONL -> SQLite -> lista de ban) com servidores-isca em processo. A Fase 1 exige
uma isca executando em container isolado, sem root, com egress negado, e
mantendo o mesmo contrato de eventos e banco.

Era necessário decidir como o agente passa a criar e supervisionar as iscas em
container sem duplicar a lógica de detecção e sem quebrar o contrato existente.

## Alternativas

1. Substituir o runtime local por Docker e remover os servidores em processo.
2. Usar apenas o honeypot Apache de laboratório em `scripts/lab/` e adaptar a CLI
   a ele.
3. Criar um runtime de container no agente, reaproveitando os mesmos servidores e
   o mesmo spool, e manter o runtime local como alternativa de desenvolvimento.
4. Orquestrar as iscas por um `docker-compose` externo e fazer o agente apenas
   ler o spool.

## Decisão

- O agente seleciona o runtime por `honeypot.runtime`: `local` (padrão) ou
  `docker`.
- O runtime `docker` (`DockerHoneypotManager`) cria um container por isca via
  CLI do Docker, com `--cap-drop ALL`, `--security-opt no-new-privileges`,
  `--read-only` + `tmpfs /tmp`, limites de CPU/RAM/PIDs, `--user` não-root e
  `--network` interna criada com `--internal` (sem egress). Nenhum container
  recebe `docker.sock` nem `--privileged`.
- O container reutiliza os mesmos servidores-isca e o mesmo `SpoolWriter`, com
  um entrypoint próprio (`python -m sentineliot.honeypot.container`) que lê
  `SENTINELIOT_HONEYPOT_ID`, `SENTINELIOT_HONEYPOT_PROFILE`,
  `SENTINELIOT_HONEYPOT_PORT` e `SENTINELIOT_SPOOL_FILE`.
- O spool JSONL é compartilhado por volume (`data/spool` -> `/spool`), então o
  coletor, o SQLite e a lista de ban não mudam.
- A imagem, o `docker-compose.yml` de referência e o teste de isolamento ficam em
  `deploy/honeypot/`.
- O agente continua fora do container e sem privilégios administrativos; o
  bloqueio real permanece fora de escopo (Fase 5).

## Justificativa

Mantém um único pipeline de eventos e uma única CLI, permitindo alternar entre
desenvolvimento local e homologação em container sem reescrever detecção,
armazenamento ou decisão. O isolamento é aplicado no momento da criação do
container, de forma auditável e reproduzível, e o container não recebe nenhuma
credencial ou caminho sensível.

## Consequências

- `honeypot.runtime: docker` exige CLI e daemon do Docker acessíveis; o comando
  `diagnostics` sinaliza indisponibilidade.
- O runtime local permanece suportado para desenvolvimento e testes rápidos.
- A imagem precisa ser construída onde houver base disponível; a VM offline
  exige pré-carregar a imagem base ou usar `docker save`/`docker load`.
- O runtime `docker` é destinado ao Linux; no Windows o runtime `local` continua
  sendo o padrão.

## Riscos

- Divergência entre o comportamento local e o do container (mitigada por usar os
  mesmos servidores e o mesmo spool).
- Publicação de porta na rede interna precisa ser revalidada no laboratório
  (ADR-0002 e ADR-0004 continuam pendentes de evidência na VM).
- Orfãos de containers se o agente for encerrado abruptamente; mitigado pela
  reconciliação por rótulo (`sentineliot.managed=true`) a cada `sync` e no
  `stop_all`.
- Uso de `--user` com o UID do agente para permitir escrita no volume; requer
  atenção às permissões do diretório de spool.
